# 테스트 방법 — 무엇을 테스트했는가

이번 테스트는 통제된 연구 평가가 아니라 도구 셋업 및 베이스라인 파이프라인
테스트입니다. 목적은 툴체인이 정상 작동하는지 확인하고, 로컬 LLM의 라우팅
동작을 초기 단계에서 살펴보는 것이었습니다.

## 테스트한 구성 요소

- Google Cloud 음성 인식 (클라우드 STT)
- 로컬 faster-whisper 음성 인식 (로컬 STT)
- Ollama 기반 Llama 3.2 (로컬 LLM, 라우팅 및 응답 생성 담당)
- Google Cloud 음성 합성 (클라우드 TTS)
- 로컬 Piper 음성 합성 (로컬 TTS)

## 테스트 규모

- 컴포넌트 단위 테스트 총 39회 (개별 STT / TTS / LLM 호출).
- 전체 파이프라인 테스트 총 48회 (오디오 입력 → 음성 응답 출력).
- 오디오 시나리오 12개, 각 시나리오를 4가지 파이프라인 조합으로 실행
  (12 × 4 = 48).

## 파이프라인 조합

모든 시나리오는 STT와 TTS 제공자의 네 가지 조합 전체에 대해 실행했으며,
라우팅을 담당하는 로컬 LLM(Llama 3.2)은 항상 동일하게 사용했습니다.

1. Google STT + Llama 3.2 + Google TTS
2. Google STT + Llama 3.2 + 로컬 Piper TTS
3. 로컬 faster-whisper STT + Llama 3.2 + Google TTS
4. 로컬 faster-whisper STT + Llama 3.2 + 로컬 Piper TTS

## 라우팅 판단 기준

LLM의 라우팅 판단은 `config/routes.json`에 정의된 경로 트리를 기준으로
검증했습니다. 이 "검증"(`route_valid`)이 실제로 의미하는 것과 의미하지
않는 것에 대해서는 `RESULTS_INTERPRETATION_KR.md`를 참고하시기 바랍니다.

## 범위에 대한 참고 사항

이번 테스트에서 Llama 3.2를 사용한 이유는 이미 설치되어 있는 편리한 로컬
베이스라인 모델이기 때문이며, 최종적으로 제안할 아키텍처가 아닙니다. 이
단계에서 발생하는 오류들은 예상된 것이며, 파이프라인 설계 자체에 대한
평가라기보다는 향후 아키텍처가 다뤄야 할 부분을 알려주는 유용한 신호로
취급하고 있습니다.
